# AGENTS.md — карта для агентов и разработчиков

Telegram-бот, который из двух дорожек (каждый ведущий записан у себя, обычно удалённо через звонок) собирает готовый выпуск подкаста. Он синхронизирует дорожки, обрезает по смыслу, обрабатывает звук, ставит заставки, делает таймкоды, расшифровку и описание. Двое ведущих видят ход сборки в живой карточке, проверяют превью и одобряют выпуск.

Человеческое описание — в [README.md](README.md), планы — в [ROADMAP.md](ROADMAP.md). Здесь — как устроен код и как его безопасно менять.

## Конвейер (core/src/podcast_core/pipeline.py)

```
tracks/A, tracks/B
  │ analyze ─────────────► sync.json        сдвиг offset, дрейф drift, ручная поправка b_delay, сегменты речи;
  │                                         если в meta.sync_marks есть нажатия синхросигнала — mode "signal"
  │ transcribe ──────────► transcript.json  AssemblyAI multichannel: канал 1 = A, канал 2 = B (+ apply_spelling)
  │ make_plan ───────────► plan.json        LLM: start/end (+фразы → точное время по словам), title, description, chapters
  │ measure_levels ──────► levels.json      громкость и порог гейта каждой дорожки по [start, end], с EQ; кэш по ключу
  │ auto_eq ─────────────► auto_eq.json     только если у ведущего профиль «авто»: спектры голосов → EQ к среднему
  │ render(preview=True) ► preview/         заставка + первая минута
  └ render() ────────────► out/             «<имя> №N.mp3», caption.txt, description.txt, chapters.*, transcript.*
```

- **Шкала времени — везде дорожка A, в секундах** («сырой» таймлайн до обрезки). Дорожка B переводится на неё как `t_B = offset − b_delay + (1+drift)·t_A` (`b_align_filter`). В шкалу готового MP3 переводит `shift = t − start + t_main`, где `t_main` — момент конца заставки.
- **Каждый этап кэширует результат в папке выпуска.** `run()` пропускает готовые этапы. Чтобы переделать этап, удали его файл: `plan.json` — чтобы заново спросить LLM, `levels.json` — чтобы перемерить громкость.
- **Настройки:** `DEFAULTS` ← `settings.json` (общие) ← `<job>/settings.json` (правки одного выпуска из кнопок превью: `eq`, `comp_ratio`, `track_profile`, `deesser`, `dynaudnorm`, `denoise`/`denoise_nr`). Полный список ключей — `DEFAULTS` в `core/src/podcast_core/pipeline.py`.
- **EQ голосов:** `track_eq(cfg, work, span)` — по `track_profile` → `mic_profiles` (имя → фильтры ffmpeg), профиль `"авто"` → `auto_eq()`: средний спектр речи каждого голоса по октавам 250–8000 Гц (ниже не трогаем — там разница мужского и женского голоса), оба тянутся к среднему, не больше ±4 дБ. Без `track_profile` — старый список `track_eq`. После EQ — `deesser`, `dynaudnorm` (окно ~4 с, усиление ≤ ×3).
- **Промежуточные дорожки** — WavPack float (`tmp_codec`): без потерь и примерно вдвое меньше WAV; удаляются после сборки.
- **LLM:** `llm(prompt, key, cfg)` — основная модель OpenRouter → `openrouter_fallbacks` → AssemblyAI LLM Gateway; в `plan.json` пишется `llm_model_used`.
- **Прогресс:** `progress(key, доля, info=…)`. Ключи этапов: `sync`, `transcribe`, `plan`, `preview`, `clean`, `mix`, `final`. ffmpeg отдаёт долю через `-progress pipe:1` (`ff(..., on_frac=, total=)`).

## Жизненный цикл выпуска (bot.py)

```
        «➕ Записали выпуск №N» или первый файл
                     │
                 waiting ──(обе дорожки)──► grace (30 с на замену файла) ──► processing[run]
                     ▲                                                          │ sync → transcribe → plan → preview
                     │                                                          ▼
                cancelled                         ┌──────────────────────── preview ◄──┐
                                                  │ «✅ Собирай полный»        │ правки: начало/конец, EQ,
                                                  ▼                            │ компрессор, сдвиг ±100 мс
                                         processing[render]                    └──► processing[preview]
                                                  │ clean → mix → final
                                                  ▼
                       правки (обрезка, главы, EQ) ◄── review ──(✅ оба)──► approved
                       → processing[render]
  любой этап с ошибкой → failed («🔁 Ещё раз» повторяет тот же mode)
```

- **Состояние** — `/data/state2.json`: `offset` (getUpdates), `last_n`, `ep` (текущий выпуск), `await` (чего бот ждёт от каждого: обрезку, главы, заставку), `history`. Пишется атомарно (`P.jsave`) после каждого апдейта.
- **`ep`**: `n`, `status`, `mode`, `stage_keys`, `stages{key: {st, frac, info}}`, `tracks{uid: {path, file, dur, ok}}`, `job` (папка), `cards{uid: message_id}`, `approvals{uid: bool}`, `preview`, `report`, `eta`, `test_to`, флаги напоминаний.
- **Карточка** — одно сообщение на ведущего, закреплено. `card(uid)` строит её целиком из `ep` для любого состояния. `flush_cards()` правит обе на месте (во время сборки не чаще раза в 4 с). `new_card()` присылает заново внизу: при старте сборки, после доставки, по нажатию на статус.
- **Нижняя клавиатура** (`reply_kb`) — статус и «➕ Записали выпуск». Telegram обновляет её только вместе с новым сообщением, поэтому она приезжает с событиями (`event()`).
- **Потоки:** главный (long polling) и `worker` (сборка, по очереди) работают под общим `RLock` (`lock`). `ticker` раз в 5 с: отсчёт до старта и напоминания. `cleanup` раз в сутки удаляет старые исходники.

## Синхросигнал

**Зачем.** Синхронизация по разговору даёт 50–100 мс и ничего не знает о реальном времени. Короткий свист (`CHIRP`: 0,6 с, 800→3200 Гц), который звучит у обоих в точно известный момент по часам бота, даёт точность сверки часов (на практике ±3…30 мс). Два сигнала («начало» и «конец») дают ещё и разницу хода часов устройств.

**Мини-приложение** (`webapp.html`) открывается **кнопкой меню бота** «🔔 Синхро» (`setChatMenuButton`, тип `web_app`, ставится в `main()`). Не из кнопки нижней клавиатуры: туда Telegram не передаёт `initData`.
1. **Звук.** Браузер не даёт странице звук без нажатия. Первое нажатие любой кнопки («🔈 Проверить звук» или «Я готов») создаёт `AudioContext` (`ensureAudio`). На iOS: `navigator.audioSession.type = "playback"`, чтобы не глушил переключатель «бесшумно», и `ctx.resume()` перед каждым звуком (`wakeAudio`), потому что после сворачивания звук «засыпает». «Я готов» ставит `ready`: только тогда общий сигнал играет и на этом устройстве.
2. **Часы.** `GET time` — замер «вопрос-ответ», раз в 15 с по 4 замера, копятся 10 минут. `offset` — медиана замеров с быстрым ответом (rtt ≤ 1,3·min + 15 мс). Точность `err` — их разброс; `rtt` — самый быстрый ответ. На экране «часы ±err (сеть rtt)». rtt/2 — лишь худший случай: задержка сети при симметричном пути вычитается (пример: сеть 150 мс, часы ±4 мс).
3. **Присутствие.** Раз в 0,7 с `POST api {op: ping, ready, err, rtt}`. Бот хранит `PRESENCE` («в сети» — ping не старше 3 с) и отвечает списком ведущих (в сети / готов / точность / сколько сигналов у выпуска), номером выпуска `n` и активным общим сигналом.
4. **Общий сигнал.** Любой жмёт «Сигнал»: `op: fire` → `FIRE.T = сейчас + 2 с` (столько нужно, чтобы команда дошла до второго устройства через опрос). Каждое готовое устройство проигрывает чирп ровно в `T` (WebAudio, `getOutputTimestamp`, поправка на `outputLatency`) и шлёт `op: mark {t: T, lat}`.
5. **Доступ.** Подпись `initData` (HMAC-SHA256 от токена бота, свежесть ≤ 1 ч) или токен сессии проверяются у каждого `POST api`; не ведущим — 403 и причина в логе. Без них доступны только `GET /` (страница, без данных), `GET /time` и фид. **Сессия:** «Синхро» держат открытым всю запись, а `initData` устаревает через час (так 16.10 приложение «умерло» посреди записи). Поэтому каждый ping возвращает `token` (`session_token`: `uid.exp.HMAC`, ключ — от токена бота, 12 ч, продлевается); страница хранит его в `sessionStorage` и шлёт вместе с `initData`. Пропала связь — на дисплее «ОФЛАЙН», опрос продолжается; метки, таймер и темы живут в боте, так что после переоткрытия всё на месте (нужно только снова нажать «Готов» — звук без нажатия не включить).
6. **Таймер записи** — `rec_payload(n)`: от первого сигнала выпуска («начало», самая ранняя первая отметка) до второго («конец»), в ping как `rec`; страница считает по часам сервера (`offset`).

**Отметки** хранятся в `S["marks"]` с номером выпуска `n` (`sync_n()`: открытый выпуск или следующий по счёту), точностью часов `err`, временем ответа `rtt` и задержкой вывода `lat`. Первая отметка выпуска — «начало», вторая — «конец». При старте выпуска (`start_episode`) его отметки уходят в `meta.json["sync_marks"]` (моменты по ведущим, в порядке `ORDER`) и `["sync_marks_meta"]` (качество).

**При сборке** `analyze()` ищет чирп в каждой дорожке (`find_chirps`: нормированная корреляция по 60-секундным кускам; речь даёт ≲ 0,15, сигнал 0,9+), сопоставляет с нажатиями (`match_marks`: промежутки между сигналами должны совпасть с промежутками между нажатиями) и считает `offset`/`drift` (`signal_sync`). По одному сигналу — сдвиг по сигналу, дрейф по разговору. **Страховка:** если сигнал расходится с разговором больше чем на 0,3 с (плохо сверились часы), берётся разговор, `sync["signal"]["rejected"]` и заметка в карточке. Результат по разговору всегда лежит в `sync["by_talk"]`, качество часов — в `sync["signal"]["clock_err"]` и в строке этапа «синхронизация».

**Наружу** смотрит только веб-сервер бота через отдельный узел Tailscale `podcast-pi` (контейнер `podcast-tailscale`, userspace, Funnel из `tailscale/serve.json` → `http://podcast-bot:8790`).

**Как подключён узел** (если придётся повторить):
1. Без ключа: `docker compose up -d podcast-tailscale` → ссылка входа в `docker compose logs podcast-tailscale`. Стартовый скрипт контейнера ждёт входа только 60 с и перезапускается с новой ссылкой, поэтому надёжнее войти разовым контейнером на том же томе `tsstate`: `tailscaled --tun=userspace-networking …` + `tailscale up --hostname=podcast-pi --timeout=0`.
2. В compose `TS_AUTH_ONCE=true` и `TS_HOSTNAME`: иначе служба при каждом старте повторяет `tailscale up` с другими флагами и падает.
3. В админке Tailscale у узла — **Disable key expiry** (иначе через 180 дней кнопка перестанет открываться).
4. Публичная DNS-запись `podcast-pi.<tailnet>.ts.net` появляется не сразу (бывает до получаса). Проверить Funnel до неё: `curl --resolve <имя>:443:<IP входного сервера Funnel> https://<имя>/time` (IP — из `dig` по имени любого другого вашего узла с Funnel).

## Темы будущих выпусков

Добавление — только в боте: «💡 Тема» в нижней клавиатуре → `S["await"][uid] = {kind: "topic"}` → следующий текст → `topic_add()` (второму ведущему сразу приходит с автором и inline-кнопкой web_app «🗳 Темы», `?tab=topics`). `/cancel` или любая команда/кнопка отменяет ввод. Смотрят и голосуют в мини-приложении: `POST api` с `op` = `topics` (список), `vote` (`fire|ok|no|null`), `kind` (`topic|note`), `status` (`open|next|done`; `done` ставит `n` = текущий/последний выпуск, `topic_episode()`), `tdel` (только автор) — всё в `topic_op()` под `lock`. Хранение — `S["topics"]`, `S["topic_seq"]`, `S["topics_v"]` (растёт при любой правке; ping отдаёт `tv`, страница перечитывает список, когда он изменился). «Обсудили» отмечают руками (автоотметка по главам — идея на потом).

## Правила и инварианты

1. **Всё, что отправляется ведущим, идёт через `audience()`**, не через `ORDER`. В тестовом режиме (`ep["test_to"] = uid`) получатель только один. `ORDER` нужен для смысла: каналы A/B, имена, одобрения.
2. **Состояние меняется под `lock`, после изменений — `save()`.** Внешний скрипт не должен писать `state2.json`, пока бот запущен: бот перезапишет файл из памяти. Правильно так: `docker compose stop podcast-bot` → правка → `up -d`.
3. **Порядок каналов = порядок `PEOPLE`.** A — первый ведущий (канал 1 в расшифровке), B — второй. От этого зависят `track_eq[i]`, имена в расшифровке, `b_delay` («сдвиг второго»).
4. **Полный выпуск без начала, конца и глав не выпускаем.** Если не ответила ни одна модель из цепочки, сборка падает (`failed`), а не идёт дальше.
5. **Превью и полный выпуск звучат одинаково:** оба берут усиление и гейт из `levels.json`, ключ кэша включает EQ.
6. **Веб-сервер мини-приложения публичный.** Любой новый эндпоинт — только за `check_init_data()`; тело читать только после проверки длины (≤ 8 КБ). Подробно — SECURITY.md.
7. **Долгие операции не держат `lock`.** Сборка идёт в `worker` без блокировки; `finish()`/`finish_preview()` берут `lock` только чтобы поменять состояние, а загрузку в Telegram (может идти минуты) делают без него — бот в это время отвечает на кнопки. Веб-сервер мини-приложения общий `lock` берёт только на короткие правки (отметка сигнала, темы), `PRESENCE`/`FIRE` — под своим `web_lock`.

## Запуск и проверка

```bash
# выкатка на сервер (<host> — ваш сервер, <dir> — папка с compose)
scp requirements.txt podcast.py bot.py webapp.html Dockerfile .dockerignore docker-compose.yml <host>:<dir>/ && ssh <host> 'cd <dir> && docker compose up -d --build podcast-bot'
# логи
ssh <host> 'cd <dir> && docker compose logs -f podcast-bot'
# обработка без бота (CLI)
python3 podcast.py run A.wav B.m4a --names Аня Боря --work /tmp/ep
```

- **Без Telegram.** `podcast.py` — CLI. Для отдельных этапов: `P.render(work, cfg, preview=True)`, `P.make_plan(...)` на копии папки выпуска. Копируй json, а не трогай боевую папку.
- **Карточка без Telegram.** Импортируй `bot` с `BOT_TOKEN_FILE` (любой файл), `DATA` (временная папка) и `PEOPLE` (формат — в `.env.example`), заполни `B.S["ep"]` и вызови `B.card(uid)` / `B.status_text()`. Сеть не нужна.
- **Тестовый режим на живом боте.** Останови бота, в `state2.json` поставь `ep.test_to = <uid>` и нужный `status`/`mode`, запусти. Выключить — убрать `test_to` и вернуть статус, карточки поправить через `flush_cards()`.
- **Звук:** `tools/miccheck.py <job>` — спектры исходников, `tools/eqcheck.py <job>` — эффект пресетов. Команды запуска — в шапке файлов.

## Типовые задачи

| Задача | Где |
|---|---|
| Новая кнопка в карточке | `card()` — кнопка через `btn(text, data, style, disabled)`, обработка — ветка в `on_callback()`. Правка, требующая пересборки, вызывает `begin_processing(mode)`. |
| Новый этап сборки | Ключ и подпись в `STAGES`, ожидаемое время в `EXPECT`, ключ в `MODE_KEYS[mode]`; в `podcast.py` — вызовы `progress(key, …)`. |
| Поменять звук | Пресеты голосов — `track_eq` в настройках (строки фильтров ffmpeg); громкость, компрессор, лимитер — `DEFAULTS`; цепочка — `render()`. |
| Поменять, как ищется начало и конец | `PROMPT` и `transcript_for_llm()` (края — по предложениям); точное время — `find_phrase()`. |
| Вырез куска | `cuts.add_cut` (ручной, из `on_message` → ветка `kind == "cut"`); отмена — `cuts.remove_last_cut`. Края привязываются к паузам: `XF` = 0,4 с кроссфейд — окно `[from − XF, from]` и `[to, to + XF]` должно лежать в тишине. Правки обрезки/глав после выреза обязаны идти через `cuts.apply_edits` (у `P.apply_edits` времена не знают о вырезах). `finish(rep, quiet=True)` — доставка без новых карточек (ручная пересборка): MP3 + архив с припиской, карточки правятся на месте. |
| Длина и состав превью | `preview_segments()`. Если кусков больше одного, `render()` склеивает их кроссфейдом `XF`. |
| Публикация после одобрения | `publish()` (поток после одобрения обоих): `publish_feed()` → `feed.add_episode()` (номер уже в фиде — не дублирует; описание: `summary` + `feed_footer_html` + таймкоды + `feed_footnotes` из настроек), затем `sendAudio` по сохранённому `ep["audio_id"]` в `PUBLISH_CHAT`, ссылка — в `ep["published"]` и в карточке. В тестовом режиме не публикует. |
| Новый переключатель звука в превью | Ключ в `DEFAULTS` и в цепочке `render()`; кнопка в ветке `preview` функции `card()`, обработка — в ветке превью `on_callback()` (пишет в `<job>/settings.json` и вызывает `begin_processing("preview")`); поле в отчёте превью (`rep` в `render(preview=True)`). |

## Грабли (проверено на живых выпусках)

- **Хлопки для синхронизации через звонок не работают.** Каждый слышит другого с задержкой, хлопки в дорожках расходятся на секунды. Синхронизация идёт по самому разговору (`analyze`).
- **AssemblyAI `custom_spelling`:** замена (`to`) — только одно слово, иначе HTTP 400. Свои замены — ключ `spelling` в настройках, применяются в `apply_spelling()`.
- **AssemblyAI LLM Gateway** на демо-аккаунте пускает только `qwen3.5-4b-32k-fast`, поэтому LLM идёт через OpenRouter (`deepseek/deepseek-v4.1-flash`).
- **DeepSeek с «размышлениями» иногда возвращает пустой `content`:** весь лимит токенов уходит на рассуждения. Отсюда `reasoning: {effort: low}`, `max_tokens` с запасом и три попытки в `llm()`.
- **LLM ставит начало на первое приветствие,** даже если оно было пробным («Поехали. Всем привет…», а потом снова подготовка). Промпт явно описывает сорванные дубли; края расшифровки идут по предложениям с точным временем; точка начала уточняется по словам.
- **LLM иногда отдаёт время строкой** («01:23», «105s») вместо числа — всё время из плана проходит через `parse_ts()`.
- **`loudnorm` для замера медленный** (минуты на час аудио, «зависание» прогресса на 79%). Меряем через `ebur128=peak=true` — те же цифры, в разы быстрее.
- **`alimiter` без передискретизации пропускает межсэмпловые пики** (было −0,7 dBTP при цели −1,5). Лимитер работает на 4× частоте.
- **Служебное «бот закрепил сообщение» приходит как апдейт от самого бота.** Без фильтра бот отвечал себе «закрытый бот, твой ID…». В `handle()` такие сообщения удаляются.
- **Цитаты начала и конца собираются из реплик, а не из слов:** при одновременной речи слова двух каналов чередуются по времени, и строки рвались на каждом слове (`quotes()`).
- **Один EQ после сведения действует на оба голоса одинаково,** но голоса записаны разными устройствами (например, направленный рекордер близко ко рту — много баса; телефон в режиме сжатия — нет низа и обрыв выше 16 кГц). Поэтому EQ ставится на каждую дорожку до сведения (`track_eq`).
- **Локальный Bot API:** перед первым запуском бот нужно разлогинить из облачного API (`logOut`). Файлы, скачанные через `getFile`, лежат в общем томе `tgapi` — бот копирует и удаляет их.
- **Синхросигнал на iPhone, который сам пишет Диктофон,** проигрывать нельзя: iOS может прервать запись. Запускать с ноутбука или другого устройства рядом.
- **Бот не от root — uid 101 + группа хоста.** Локальный Bot API жёстко работает как `telegram-bot-api` (uid 101) и кладёт скачанное с правами 0600; под другим uid бот их не прочитает. Папка данных — `chown 101:<группа хоста>`, `g+rwX`; секреты — 640; umask бота 007.
- **Синхросигнал против разговора** пишется в `jobs/signal_stats.jsonl` (`delta_ms`, точность часов) и в заметку карточки — копим статистику на живых записях.
- **Мини-приложение из кнопки нижней клавиатуры (`KeyboardButton.web_app`) открывается без `initData`** — подпись не проверить, бот отвечал «только из бота». Подпись есть при запуске из кнопки меню (`setChatMenuButton`) или из inline-кнопки.
- **Ссылка входа Tailscale из контейнера живёт минуту** (стартовый скрипт перезапускается), а публичная DNS-запись Funnel для нового узла появляется с задержкой — см. «Как подключён узел».
- **На iOS звук страницы глушится переключателем «бесшумно» и «засыпает» после сворачивания** — `audioSession = playback` и `resume()` перед каждым звуком.
- **Мини-приложение Telegram открывается только по https.** Отсюда Funnel; страница работает и в браузере (для отладки), но отметку без `initData` бот не примет.
- **Миниатюра аудио в Telegram — только JPEG ≤ 320×320 и ≤ 200 КБ,** иначе `sendAudio` отказывает целиком. Поэтому `tg_thumb()` делает уменьшенную копию обложки (`thumb.jpg` в папке выпуска), а в MP3 обложка вшивается в полном размере.
- **Площадки забирают выпуски только из RSS, загрузку по API никто не принимает.** Поэтому фид отдаёт сам бот (`/feed.xml`, `/media/…` с `Range` — Apple без докачки не принимает). При переносе guid выпусков менять нельзя — иначе дубли. Cloudflare и GitHub как хостинг не годятся: из России (слушатели и сервера Яндекса) работают с перебоями.
- **`agate` и `alimiter` в ffmpeg принимают линейные значения, не дБ** — переводим через `db2lin`. У `alimiter` обязательно `level=0`, иначе он сам нормализует громкость.
